# Focal Point 2.0 Design Principles

STATUS: FUTURE / DESIGN DIRECTION - NOT IMPLEMENTED CURRENT ARCHITECTURE

This document captures discussed product and UX direction for later 2.0 work. It is not a final roadmap and not an implementation commitment.

## Target feeling

Focal Point should feel more like a continuous visual unit-frame editor. 2.0 should not primarily mean more features; it should mean less context loss, less manual transfer, and a clearer mental model.

## Principles

### 1. Keep Context

A tool switch should not lose known editing context. If the user is currently editing a text, unit, or property, the next tool should be able to receive that context.

### 2. Select What You See

Visible elements should lead to the relevant editing surface whenever practical. Frames and text already show that object-centered editing can work well.

### 3. Insert, Don't Transfer

Addon-internal information should be inserted or applied directly instead of being moved through the clipboard between Focal Point tools. External clipboard use for export/import remains legitimate.

### 4. Precision Second

Direct or contextual editing first; the Inspector as the precision tool. The Inspector remains important, but it should not be the first path for every visual task.

### 5. One Product Model

UX simplification must not create a second data or runtime truth. A new view should remain a projection of the existing canonical unit configuration unless a deliberate architecture decision says otherwise.

### 6. Composition / building-block mental model

Long-term, the user should think more like this:

> A unit is made of building blocks/components that I can select and style.

instead of:

> A unit has a very long list of settings.

Example building blocks: Health Bar, Power Bar, Normal Absorb Bar, Healing Absorb Bar, Cast Bar, Text, Auras, Decorations.

Important boundaries:

- This is first a mental/visual product model.
- It does not automatically introduce a second stored `FrameModel`.
- A later Component View should, if possible, be a projection of the existing unit configuration.
- It is not yet decided which components become add/remove-capable.
- It is not yet decided that every visible component gets direct handles.

## Findings from the workflow audit

- Direct frame editing is strong.
- Text positioning is object-centered and strong.
- Media Library is a good contextual picker pattern.
- Text Builder and Tag Database currently lose context and use copy/paste as a human integration layer.
- The Inspector is valuable for precision, but it has historically grown into a collection surface for many functions.
- Profile/Preset/Automation are conceptually stable and should not be remodeled without a strong reason.
- Demo/Unlock are powerful but need a clear mental distinction.

## Non-goals for this document

- no technical implementation,
- no new stored model layer,
- no concrete UI specification,
- no final roadmap,
- no promise that all visible components become directly manipulable.
